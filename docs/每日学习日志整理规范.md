# 每日学习日志整理规范

> 版本：2.1
> 用途：将每天的手记、代码、项目资料和实践结果整理为真实、简洁、便于长期复习的 Markdown 学习日志。

## 1. 每次提供的材料

- 日期与今日主题；
- 当天手记；
- 当天代码、项目目录或代码差异；
- 必要的课程资料、设计文档、API 规范、截图或报错；
- 明确的今日学习范围；
- 需要去重时提供往期日志或已整理知识点。

最简调用：

```text
请按《每日学习日志整理规范》整理今天的日志。

日期：<YYYY-MM-DD>
手记：<附件或路径>
代码/项目：<附件或路径>
参考资料：<可选>
今日范围：<学到的章节、功能或文件>
往期日志：<需要去重时提供>

只读分析，不修改源码。生成 Markdown 文件，不自动提交 GitHub。
```

## 2. 核心原则

### 2.1 只写当天真实学习的内容

- 只整理用户指定的范围；
- 项目包含完整系统时，只写今天涉及的模块；
- 新旧代码混在一起时，先区分当天新增或首次理解的内容；
- 参考文档只用于理解课程目标，不能扩大今日范围；
- 无法可靠判断范围时先简短询问。

### 2.2 以实际证据为准

判断优先级：

1. 用户提供的运行结果、测试结果和报错；
2. 实际代码；
3. 手记和代码注释；
4. 课程参考文档；
5. 视频目录或课程计划。

必须区分：

- 文档计划不等于已经实现；
- 函数存在不等于实际调用；
- 看过概念不等于做过实践；
- 跟随教程完成不等于能够独立实现。

证据判断是模型的内部整理过程。不要在日志中解释“未提供手记”“缺少 Git 历史”“模型检查了哪些文件”或“模型依据什么推断今日范围”。只有会影响学习进度的事实才写入日志，例如用户实际尚未完成接口联调。

### 2.3 避免跨天重复

往期已详细整理的内容不再重复定义、参数或相同代码，只说明它在今天的新场景中的作用。重点记录新的组合方式、业务流程和理解变化。

以下情况可以重新展开：

- 今天首次独立实现；
- 从单文件练习进入真实项目；
- 修正了以前的错误理解；
- 出现了新的实际问题或应用场景；
- 用户明确要求专题复习。

## 3. 先检查代码，再生成日志

整理项目日志时采用两阶段流程。

### 第一阶段：代码检查

如发现以下情况，先在对话中简短列出位置、现象和建议，暂停生成日志，等待用户审查或修改：

- 明显的字段名、变量名或拼写错误；
- 未使用的导入、重复代码或明显无效代码；
- 会直接影响当前课程功能运行的明确错误；
- 明文密码、Token、API Key 等安全风险。

不要直接修改源码。用户确认无需处理，或修改后要求继续时，再进入日志生成阶段。

### 第二阶段：日志生成

- 不把第一阶段发现的拼写、冗余代码和静态审查意见写入学习日志；
- 不把模型自行执行的语法检查、静态检查或材料分析过程写成用户的学习产出；
- “遇到的问题”只记录用户当天实际遇到、排查或解决，并且有复习价值的问题；
- 不主动审查课程尚未讲解的完整性，不罗列输入长度、空值处理、并发、性能、事务优化等常规待完善项；
- 只有问题已经影响当前功能、用户实际处理过，或用户明确要求代码审查时，才展开说明。

## 4. 怎样阅读材料

### 手记

用来确定今日范围和学习重点。纠正理解错误时保持克制，不因手记简短而补充大量课外知识。

### 代码

重点查看实际使用的函数、路由、参数和模块协作，解释“为什么这样做”和“怎样执行”，不逐行翻译代码。

项目较大时沿实际调用关系阅读：

```text
应用入口
→ 路由
→ 请求参数或数据模型
→ 业务逻辑
→ 数据访问
→ 数据库、缓存或外部服务
→ 响应
```

### 参考文档

只用于理解课程目标和当天代码，不默认生成“代码与 API 规范差异”章节。即使发现一般差异，也不写入日志；只有差异直接造成当天实际报错，或用户明确要求对比时才说明。

## 5. 掌握程度

| 状态 | 判断标准 |
| --- | --- |
| 尚未实践 | 只在视频、手记或文档中看到 |
| 跟随教程完成 | 代码已写出，但还不能脱离教程复现 |
| 初步理解 | 能解释用途和主要流程，独立编写仍需查资料 |
| 已完成基础使用 | 已运行并理解主要步骤 |
| 独立完成 | 能脱离完整示例实现并自行排查问题 |
| 需要重点巩固 | 容易混淆或无法解释关键流程 |
| 尚未完成 | 功能、代码或测试还缺少关键部分 |

不要仅凭代码存在判断为已经掌握。

## 6. 默认日志结构

按当天材料灵活删减，不为保持形式填写空章节。

### 必需章节

1. **今日概览**：直接概括今天学了什么、实现了什么、推进到哪里；只面向学习者，不写材料缺失、判断依据或模型工作过程；
2. **今日知识点**：用途、涉及模块、关键实现和执行过程；
3. **今日实践与产出**：用户实际编写、运行或验证的内容；
4. **掌握情况**：知识点、当前状态和具体验收方法；
5. **容易遗忘或混淆的内容**：关键机制、调用关系和字段转换；
6. **今日总结**：今天真正建立的能力；
7. **复习检查**：默认 5 题，根据内容控制在 4～6 题；
8. **下一步**：2～3 项与课程当前进度紧密相关的任务。

### 条件章节

- 今日学习范围；
- 项目目标与相关模块；
- 核心执行流程；
- 遇到的问题与排查过程，仅限用户当天实际经历的问题。

默认不设置“代码与 API 规范差异”“代码审查发现”“潜在问题”章节。

掌握情况使用：

```markdown
| 内容 | 当前状态 | 验收方法 |
| --- | --- | --- |
```

验收方法应当可执行，例如“脱离教程重新实现注册接口”，不要只写“继续复习”。

## 7. 代码、写作与安全

- 只展示帮助理解的关键代码，不复制完整文件；
- 不增加“Day N 完整示例”，不重复粘贴同一段代码；
- 建议代码必须标明“建议写法”；
- 使用中文，先讲用途和关系，再讲必要语法；
- 写成学习日志，不写成代码审查报告、百科或课程逐字稿；
- 不加入当天未学习的内容，不夸大掌握程度；
- 不记录密码、API Key、Token、Cookie、私钥或真实连接凭据；
- 发现明文凭据时先在对话中提醒，不复制到日志。

- 源码未被修改，文件名符合规范。
