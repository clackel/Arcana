# Docker：概念、功能与使用边界

## 1. Docker 是什么

Docker 用来将应用及其依赖、必要的运行环境制成镜像，再以容器形式运行。

它解决的典型问题是：项目在自己的电脑上能运行，换到别人的电脑或服务器后，却因为环境不同而运行失败。

基本流程：

```text
项目代码 + 依赖说明 + Dockerfile
              ↓ 构建
             镜像
              ↓ 创建并启动
             容器
```

前期整理好构建和运行配置后，就可以用少量操作重复启动项目。密码、端口、数据存储和外部服务等配置，仍需要明确提供。

Docker 不会自动识别并复制本机安装的所有软件；需要在构建步骤中声明项目所需的环境和依赖。

## 2. 四个核心概念

| 概念                 | 作用                               | 类比                 |
| -------------------- | ---------------------------------- | -------------------- |
| Dockerfile           | 描述如何构建镜像，以及默认如何启动 | 制作说明书           |
| 镜像（Image）        | 包含文件、依赖和运行配置的模板     | 做好的应用运行包     |
| 容器（Container）    | 根据镜像创建的运行实例             | 正在使用的一份实例   |
| 镜像仓库（Registry） | 保存和分发镜像                     | 应用运行包的仓储平台 |

一个镜像可以创建多个容器，各容器可以拥有不同的运行配置和可写数据。

镜像不是完整虚拟机。容器通常共享宿主环境的内核；Windows、macOS 上运行 Linux 容器时，一般由 Linux 虚拟机提供内核。目标机器的操作系统、CPU 架构等仍需与镜像兼容，必要时构建多平台镜像。

## 3. 运行位置与端口映射

服务运行在 Docker 引擎所在的机器上：本机的 Docker 就使用本机资源，服务器上的 Docker 就使用服务器资源。如果终端连接的是远程 Docker 引擎，实际运行位置也是远程机器。

Docker 不会自动把项目上传到云端。让互联网用户访问服务，还需要可达的服务器、网络和相应的访问配置。

### 端口映射

容器有自己的网络环境。让电脑上的程序访问容器内服务，常用端口映射：

```text
电脑上的客户端
      ↓ 127.0.0.1:15432
Docker 端口映射
      ↓ 容器端口 5432
PostgreSQL 数据库
```

映射需要显式配置，例如 `-p 127.0.0.1:15432:5432`。Docker 根据配置转发流量，不会自动决定映射哪些端口。

- 本机访问时使用本机端口 `15432`。
- 容器内数据库仍监听 `5432`。
- `127.0.0.1` 绑定用于限制本机访问。
- Dockerfile 中的 `EXPOSE` 只是端口声明，不等于端口映射。

## 4. 镜像构建与 Dockerfile

Dockerfile 通常描述四件事：选择基础环境、安装依赖、复制或编译项目、设置启动命令。

| 常用指令     | 含义                                            |
| ------------ | ----------------------------------------------- |
| `FROM`       | 选择基础镜像，如 Python 或 Java 运行环境        |
| `WORKDIR`    | 设置镜像内的工作目录                            |
| `COPY`       | 将构建上下文中的文件复制进镜像                  |
| `RUN`        | 构建时执行命令，如安装依赖、编译代码            |
| `CMD`        | 设置容器启动时的默认命令或参数                  |
| `ENTRYPOINT` | 设置容器启动的主程序，可搭配 `CMD` 提供默认参数 |
| `ENV`        | 设置环境变量，容器运行时也可用                  |
| `ARG`        | 提供构建时参数，不自动成为容器运行时环境变量    |
| `EXPOSE`     | 声明服务预计监听的端口                          |

最重要的区别：**`RUN` 在构建时执行，`CMD` 在启动容器时使用。**

`.dockerignore` 排除不需要参与构建的内容，如 Git 历史、本机虚拟环境、日志和敏感配置。

端口映射、数据挂载和不同环境的配置，通常放在运行命令或 Compose 配置中。密码、API 密钥不应打进镜像，`ARG` 也不适合传递构建秘密。

## 5. 服务拆分与 Compose

一个项目不一定装进一个容器。常见拆法是按服务分开：

```text
项目
├── 后端容器
├── 数据库容器
└── Redis 容器
```

这样可以分别更新、重启和配置各个服务。数据库、Redis 等通常直接使用现成镜像，业务服务再编写自己的 Dockerfile。

### Compose 的作用

`compose.yaml` 描述多个服务如何配合运行，包括：

- 使用什么镜像，或从哪里构建镜像。
- 环境变量、端口映射、数据卷。
- 加入哪些网络。
- 启动依赖、健康检查等。

**Dockerfile 负责一个服务的镜像怎么制作；Compose 负责整个项目的服务怎么运行。**

Compose 不会把多个镜像合并成一个大镜像。它也不是必需的，只是将原本需要手动执行的多项操作保存成可重复使用的配置。

一起启动不等于一起准备就绪。后端可能需要等待数据库完成初始化，因此要有连接重试，或配置健康检查与依赖条件。

## 6. 容器网络与通信

以下讨论同一台 Docker 主机上常见的 bridge 网络。

可以把自定义 Docker 网络理解为虚拟局域网。加入同一网络的容器通常可以通过容器名和内部端口连接，例如后端连接 `db:5432`。

| 网络方式                     | IP 通信              | 自动名称解析     |
| ---------------------------- | -------------------- | ---------------- |
| Docker 自带的默认 `bridge`   | 默认允许同网容器通信 | 不自动解析容器名 |
| 手动创建的自定义 bridge 网络 | 支持                 | 支持容器名或别名 |
| Compose 自动创建的项目网络   | 支持                 | 支持服务名       |

不手动创建网络，通常意味着使用了已有的默认网络，而不是没有网络。

Compose 默认会为项目创建网络，并把服务加入其中。这是它自动执行的配置，不是容器一起启动就天然互通。

通信规则：

- **同一自定义网络内的容器通信，一般不需要端口映射。**
- **容器内的 `localhost` 指向该容器自己。** 后端连接数据库容器时应使用数据库服务名。
- 服务需要监听可被容器网络访问的接口，并通过数据库认证等应用层检查。
- 不同 bridge 网络默认隔离，不是知道容器名就能连接。
- 容器 IP 可能随重建变化，优先使用服务名。

## 7. 数据库容器与持久化存储

连接方式依然是“地址 + 端口 + 用户名 + 密码 + 数据库名”。

假设数据库服务名为 `db`，内部端口为 `5432`，映射到本机 `15432`：

| 从哪里连接                 | 连接地址          |
| -------------------------- | ----------------- |
| 本机数据库客户端或本机后端 | `127.0.0.1:15432` |
| 同一自定义网络中的后端容器 | `db:5432`         |

### 存储方式与数据生命周期

| 操作或存储方式         | 数据变化                               |
| ---------------------- | -------------------------------------- |
| 停止容器               | 容器及其可写层保留                     |
| 删除容器               | 容器可写层随之删除                     |
| 数据卷（Volume）       | 独立于容器管理，删除容器通常不会删除卷 |
| 目录挂载（Bind mount） | 数据位于指定的宿主机目录               |

数据库数据、用户上传文件等需要持久化存储。**数据卷不是备份**，机器故障或误删仍可能导致数据丢失。

## 8. 应用更新与容器生命周期

通过 `COPY` 放进镜像的是构建时的一份文件。修改本机代码，已有镜像和容器不会自动变化。

典型更新流程：

```text
修改代码 → 构建新镜像 → 用新镜像重新创建容器
```

仅重启旧容器不会让它切换到新镜像。

开发时可以挂载本机代码目录，让容器读取修改后的文件；程序是否自动重新加载，还取决于框架是否支持热重载。

容器通常围绕主进程运行。主进程退出，容器也会停止。脚本正常执行完后容器停止，并不一定是故障。

## 9. 镜像分发与镜像仓库

镜像分发用于把构建好的应用交给其他机器运行：

```text
构建镜像 → 上传镜像仓库 → 服务器下载 → 配置并启动容器
```

Docker 官方提供 Docker Hub，它也是默认的镜像仓库平台。还可以使用其他服务商的仓库，或公司内部自建仓库。

Docker Hub 上既有官方镜像，也有企业和普通用户发布的镜像；并不是所有内容都由 Docker 官方维护。

### 和 Maven 仓库的类比

| 对比         | Maven 仓库         | Docker 镜像仓库    |
| ------------ | ------------------ | ------------------ |
| 主要内容     | JAR、POM 等构件    | 容器镜像           |
| 常见用途     | 获取项目的代码依赖 | 获取应用及运行环境 |
| 公共平台示例 | Maven Central      | Docker Hub         |
| 企业私有仓库 | 可以搭建           | 可以搭建           |

Java 项目可以先从 Maven 仓库获取依赖、构建 JAR，再将 JAR 与 Java 运行环境制成镜像，上传到镜像仓库。

### 分发时的边界

- 镜像不自动包含数据卷里的数据库数据，数据需要单独迁移。
- Compose 配置、密码和外部服务地址需要另外提供。
- 版本标签方便选择发布版本，但标签可以被重新指向；需要精确锁定内容时使用镜像摘要（digest）。
- 保留旧镜像有助于回退应用，但数据库结构变更可能影响回退。

## 10. 构建优化：更快、更小、更容易分发

### 利用缓存，减少重复工作

Docker 可以复用未变化的构建步骤。常见组织方式是：

```text
复制依赖清单 → 安装依赖 → 复制业务代码
```

业务代码经常修改，依赖清单相对稳定。这样只改业务代码时，通常能复用依赖安装步骤，避免从头执行。

### 排除无关内容

使用 `.dockerignore` 减少构建上下文，避免日志、虚拟环境等被传入构建过程或意外复制进镜像。

### 多阶段构建

构建阶段保留编译工具，最终运行阶段只保留运行必需的产物和依赖。例如静态前端网站：

```text
构建阶段：Node.js + 源代码 + 开发依赖
                  ↓ 编译
          HTML、CSS、JavaScript
                  ↓ 复制产物
运行阶段：Web 服务器 + 编译后的文件
```

最终镜像可以不带编译工具和开发依赖，从而减少体积。基础镜像也应根据兼容性和运行需求选择，不能只追求最小。

**镜像更小通常意味着传输更快、存储更省，不代表应用处理请求一定更快。**

## 11. 常用命令

以下命令使用示例镜像名和容器名，执行时应替换为实际项目配置。

| 命令                                                            | 用途                                               |
| --------------------------------------------------------------- | -------------------------------------------------- |
| `docker build -t my-app:1.0 .`                                  | 在当前目录构建并命名镜像                           |
| `docker run -d --name my-app -p 127.0.0.1:8080:8000 my-app:1.0` | 创建并后台启动容器，供本机通过 8080 访问           |
| `docker ps -a`                                                  | 查看所有容器及状态                                 |
| `docker logs my-app`                                            | 查看容器日志                                       |
| `docker exec -it my-app sh`                                     | 在运行中的容器里打开 shell，镜像需包含 sh          |
| `docker stop my-app`                                            | 停止容器                                           |
| `docker start my-app`                                           | 启动已有的已停止容器                               |
| `docker compose up -d`                                          | 按 Compose 配置创建、更新并后台启动服务            |
| `docker compose logs -f`                                        | 持续查看项目服务日志                               |
| `docker compose down`                                           | 停止并删除项目容器和默认创建的网络；默认保留命名卷 |

镜像分发常见动作是 `push`（上传）和 `pull`（下载）；自定义网络常见动作是 `docker network create` 和 `docker network connect`。具体参数按场景配置即可。

注意：`docker compose down -v` 会额外删除相关卷，涉及持久数据时要明确后果。
