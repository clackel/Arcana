## 今日知识点

### 1. 用户登录：查询用户并验证密码

登录接口接收与注册相同的用户名和密码模型，但处理目标不同：注册负责创建用户，登录负责确认用户身份。

```text
POST /api/user/login
→ 根据 username 查询用户
→ 用户不存在：认证失败
→ 使用 bcrypt 校验明文密码与数据库哈希
→ 密码不匹配：认证失败
→ 创建或更新该用户的 Token
→ 返回 token 和 userInfo
```

`authenticate_user` 把“用户不存在”和“密码错误”都统一返回为认证失败，路由最终响应 401 和“用户名或密码错误”。这样不会通过错误信息向外暴露某个用户名是否真实存在。

密码校验使用：

```python
pwd_context.verify(plain_password, hashed_password)
```

这里传入的是用户本次输入的明文密码和数据库保存的哈希值，而不是重新比较两段明文。

### 2. Token 的创建、更新和有效期

登录成功后调用已有的 `create_token`：生成新的 UUID Token，并把过期时间设置为当前时间之后 7 天。

```text
查询该用户的 Token 记录
→ 已存在：替换 token 和 expires_at
→ 不存在：新增 UserToken 记录
```

因此，同一用户再次登录会获得新 Token，旧 Token 随记录更新而失效。Token 记录通过 `user_id` 与用户表建立关联。

Token 只是随机凭据，不直接携带用户资料。服务端仍要使用 Token 查询数据库，确认它存在、尚未过期，并找到对应用户。

### 3. 使用依赖注入获取当前用户

`get_current_user` 把多个受保护接口都需要的认证过程封装成 FastAPI 依赖：

```text
读取 Authorization 请求头
→ 去掉 Bearer 前缀，得到 Token
→ 查询 Token 记录
→ 检查 Token 是否存在、是否过期
→ 根据 user_id 查询用户
→ 无效时返回 401
→ 有效时把 User 对象注入路由
```

路由只需声明：

```python
user: User = Depends(get_current_user)
```

这样获取用户信息、更新资料和修改密码不必分别重复读取请求头、查询 Token 和处理 401，认证规则也集中在一处。

### 4. 获取当前用户信息

`GET /api/user/info` 不需要客户端再次提交用户 ID。接口从有效 Token 得到当前用户，再通过 `UserInfoResponse.model_validate(user)` 把 ORM 对象转换为公开响应数据。

这条链路体现了 Token 认证的核心作用：客户端提交的是“我持有的凭据”，服务端根据凭据确认“我是谁”。用户 ID、用户名等身份信息由服务端查询，而不是信任客户端自行声明。

### 5. 局部更新用户资料

`PUT /api/user/update` 同时依赖当前用户和数据库会话。认证依赖确认操作者身份，更新函数使用当前用户的用户名定位记录。

```python
user_data.model_dump(exclude_none=True, exclude_unset=True)
```

这一步把 Pydantic 模型转换为字典，并排除未提交或值为 `None` 的字段。随后通过 `values(**更新字典)` 只修改客户端实际提供的资料，避免一次局部更新意外覆盖其他字段。

更新提交后重新查询用户，使响应能够返回修改后的用户信息。

### 6. 修改密码

修改密码接口通过字段别名接收 `oldPassword` 和 `newPassword`，其中新密码设置了最少 6 个字符的约束。

```text
Token 鉴权得到当前用户
→ 校验 oldPassword 与当前密码哈希
→ 校验失败：不修改密码
→ 校验成功：哈希 newPassword
→ 更新用户密码并提交
→ 返回修改成功
```

旧密码验证用于防止仅获得一个已登录会话的人直接更换账号密码；新密码仍然经过 bcrypt 哈希后才保存，数据库中不会写入明文密码。

## 核心执行流程

```text
登录请求
→ 用户名与密码验证
→ 生成或更新 Token
→ 客户端保存 Token

后续受保护请求
→ Authorization 携带 Token
→ get_current_user 验证 Token
→ 查询 Token 对应用户
→ User 对象注入业务路由
→ 获取资料 / 更新资料 / 修改密码
→ 返回统一响应
```

## 遇到的问题与排查过程

### Token 能查到，但可能无法得到正确用户

在 `get_user_by_token` 中，最初使用 `db_token.id` 查询 `User.id`。

```text
现象：Token 认证链路可能查不到对应用户
→ 检查 UserToken 模型中的字段含义
→ db_token.id 是 Token 记录自己的主键
→ db_token.user_id 才是关联的用户 ID
→ 将查询条件改为 User.id == db_token.user_id
```

这个问题容易暂时被数据掩盖：当用户表 ID 与 Token 表 ID 恰好相同时，错误查询可能看起来正常；两张表的主键序列不同后才会暴露。排查关联查询时，应沿外键字段判断对象关系，不能因为两个字段都叫 `id` 就认为它们代表同一实体。

## 容易遗忘或混淆的内容

- `UserToken.id` 是 Token 表主键，`UserToken.user_id` 才是关联用户的外键；
- 登录验证使用 `verify(明文密码, 数据库哈希)`，不是把两个哈希直接比较；
- Token 有效不仅要求记录存在，还要检查 `expires_at`；
- `Depends(get_current_user)` 注入的是认证后的 `User` 对象，不只是 Token 字符串；
- 更新模型的 `exclude_unset=True` 排除未提交字段，`exclude_none=True` 还会排除显式传入的空值；
- 获取当前用户身份应依据服务端验证过的 Token，而不是相信客户端提交的用户 ID；
- 修改密码要先验证旧密码，新密码必须重新哈希后保存。
