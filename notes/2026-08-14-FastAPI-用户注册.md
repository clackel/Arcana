## 今日知识点

### 1. 用户注册的分层流程

注册接口不是简单插入一条用户记录，而是由多个模块协作完成：

```text
POST /api/user/register
→ UserRequest 校验 username、password
→ Depends(get_db) 注入 AsyncSession
→ 按用户名查询用户
→ 已存在：返回 HTTP 400
→ 不存在：哈希密码并创建用户
→ 为用户创建或更新 Token
→ ORM User 转为 UserInfoResponse
→ UserAuthResponse 组装 token 和 userInfo
→ success_response 返回统一 JSON
```

路由负责业务顺序，CRUD 负责数据库操作，Schema 负责输入与输出结构，安全工具负责密码处理。这样比把查询、哈希和响应拼装全部写在路由中更容易维护。

### 2. 注册请求模型与响应模型

`UserRequest` 接收用户名和密码：

```python
class UserRequest(BaseModel):
    username: str
    password: str
```

响应被拆成两层：`UserInfoResponse` 表示公开的用户信息，`UserAuthResponse` 再加入 Token。密码字段没有进入响应模型，因此不会被正常响应流程返回。

`ConfigDict(from_attributes=True)` 允许 Pydantic 通过对象属性读取 SQLAlchemy ORM 实例：

```python
UserInfoResponse.model_validate(user)
```

这一步解决了“数据库返回 ORM 对象，但接口需要结构明确的响应数据”的转换问题。

### 3. 字段别名与前后端命名

Python 字段使用 `user_info`，API 规范要求 JSON 中使用 `userInfo`。代码通过字段别名完成转换：

```python
user_info: UserInfoResponse = Field(..., alias="userInfo")
```

`populate_by_name=True` 允许构造模型时使用 Python 字段名，而序列化时可使用别名。实际局部验证确认认证响应的顶层键为 `token` 和 `userInfo`。

### 4. 使用 bcrypt 保存密码哈希

`CryptContext` 配置 bcrypt，并通过 `hash()` 将明文密码转为不可直接还原的哈希值：

```python
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")
hashed_password = pwd_context.hash(password)
```

今天的局部测试确认：生成结果不同于原始密码，并可使用同一密码通过 `verify()` 校验。当前注册流程只实现了哈希；真正登录时还需要编写密码验证流程。

需要注意：哈希不是加密。业务不需要、也不应该把哈希还原成明文，而是在登录时比较候选密码与哈希是否匹配。

### 5. 用户查重与创建

注册首先按用户名查询：

```python
select(User).where(User.username == username)
```

`scalar_one_or_none()` 表达“最多返回一个用户”；数据库中的用户名唯一约束则提供最终一致性保护。仅靠先查询再插入仍可能遇到并发注册，因此数据库唯一约束不可省略。

创建用户时，代码先哈希密码，再把 ORM 对象加入会话，提交后执行 `refresh(user)`。刷新用于读回数据库生成的 ID、默认头像、默认简介等字段，为后续创建 Token 和响应组装提供完整对象。

### 6. Token 的生成、有效期与复用

代码使用 UUID 字符串生成 Token，并设置 7 天有效期：

```text
生成新 Token
→ expires_at = 当前时间 + 7 天
→ 查询该用户是否已有 Token
→ 已有：替换 token 和 expires_at
→ 没有：新增 UserToken
```

这表示一个用户当前只维护一条 Token 记录，再次生成时覆盖旧值。Token 已保存到数据库，但今天还没有实现请求头认证、过期时间检查或退出登录。

### 7. 统一成功响应

`success_response` 把成功结果统一包装成：

```json
{
  "code": 200,
  "message": "注册成功",
  "data": {}
}
```

其中 `jsonable_encoder` 负责把 Pydantic 模型、日期等对象转换为 JSON 可编码的数据，再交给 `JSONResponse`。

当前只封装了成功响应。用户名重复仍由 `HTTPException` 返回 FastAPI 默认错误结构，因此成功与失败响应还没有完全统一。

## 问题与代码发现

### 1. 响应字段 `gender` 被误写成 `er`（已复现）

`UserInfoBase` 中定义了 `er`，而 ORM 和 API 规范中的字段是 `gender`。局部模型验证的实际结果包含 `er: null`，不包含 `gender`。

```text
现象：UserInfo 响应键包含 er，不包含 gender
→ 排查 Schema 与 ORM 字段
→ 原因：schemas/users.py 中字段名误写
→ 影响：响应不符合接口规范，且无法从 ORM 读取 gender
```

下一步应把 Schema 字段与 API 规范统一，并增加响应结构测试。本次只记录问题，没有修改项目源码。

### 2. 用户名和密码缺少输入限制（潜在问题）

`UserRequest` 目前只声明为字符串，没有最小长度、最大长度或空白处理。过长用户名可能直到数据库写入时才失败，空密码也可能被哈希并保存。

应根据业务规则在 Pydantic 层添加约束，并测试空值、超长值和纯空格输入。

### 3. 注册过程存在分段提交（潜在问题）

创建用户时已经提交，之后才创建 Token。如果 Token 写入失败，用户记录可能已经存在，重试注册又会被“用户名已存在”阻止。更稳妥的注册流程应把用户和 Token 视作一个事务，在两者都成功后统一提交。

### 4. Token 更新分支依赖外层提交（潜在问题）

新建 Token 的分支在 CRUD 内提交；已有 Token 的分支只修改 ORM 属性，最终依赖 `get_db` 在请求正常结束后提交。当前流程可能生效，但两个分支的事务边界不一致，阅读和测试时容易混淆。

### 5. Token 不应出现在对象调试文本中（潜在安全问题）

`UserToken.__repr__` 会包含完整 Token。如果对象被写入日志，可能泄露认证凭据。学习日志没有复制任何真实 Token；后续也应避免在日志、异常或调试输出中打印它。

### 6. 存在无用导入（代码整洁问题）

`crud/users.py` 中导入了 `exec_prefix`，当前没有使用。这不影响运行，但会增加阅读干扰，可在后续整理代码时移除。

## 容易遗忘或混淆的内容

- 密码应保存哈希值，不是可逆密文，也不能保存明文；
- `from_attributes=True` 让 Pydantic 从 ORM 属性取值，但字段名必须与 ORM 属性一致；
- Python 内部字段名与 JSON 字段名可以用 `alias` 区分；
- `model_validate(user)` 负责 ORM 到响应模型的转换，不会自动修正拼错的字段；
- 先查用户名可以提供友好提示，数据库唯一约束才是并发情况下的最终保护；
- `commit()` 把事务持久化，`refresh()` 从数据库重新加载生成值和默认值；
- 用户创建和 Token 创建共同构成一次注册，事务边界不应被无意拆开；
- Token 已生成不等于认证功能已完成，还缺少读取请求头、查找 Token、检查过期时间等流程；
- `code: 200` 是响应体字段，HTTP 状态码是协议层状态，两者不要混为一谈；
- 代码可以通过语法检查，不代表数据库表、连接和完整接口一定正常。
